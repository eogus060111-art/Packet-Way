## 1. 입력 데이터 (SPEC 2절이 가리키는 "docs/PLAN.md 1절")

### 1-1. 4구역 토폴로지 [SPEC 1-4-4]
```
 인터넷 ──(방화벽)──┬── DMZ (웹·메일)
                    ├── 내부망 (업무PC·DB·인증·SIEM)
                    └── 개발·운영 서버망
```
| 구역 | CIDR | 설명 |
|---|---|---|
| 인터넷 | (아래 3개 사설 구역에 속하지 않는 모든 IP) | 신뢰할 수 없는 외부. CIDR 을 갖지 않는 보충 구역 |
| DMZ | 172.16.10.0/24 | 외부 공개 서버 완충 구역 |
| 내부망 | 192.168.10.0/24 | 업무 PC, DB, 인증, SIEM |
| 개발·운영 서버망 | 10.20.1.0/24 | 운영 서버, 개발 서버 |

- 구역 CIDR 은 서로 겹치지 않는다. 한 IP 는 정확히 한 구역에 속한다.
- 구역 판정: IP 가 세 사설 CIDR 에 들면 그 구역, 아니면 '인터넷'.

### 1-5. 데이터 모델 (필드만 정의)
- Rule: `no`, `src`, `dst`, `service`, `action`('allow'|'deny'), `purpose`
- service 문자열 형식: `Any` 또는 `TCP 80,443` / `UDP 514` 를 쉼표로 이은 목록. 내부 표현은 `[{proto, from, to}]` 범위 배열.
- Packet: `srcIp`, `dstIp`, `proto`, `port`
- Verdict: `action`, `matched`(규칙 번호 또는 null), `warnings[]`, `trace[]`(비교한 규칙과 불일치 사유)
- HistoryEntry: `time`(ISO8601), `type`(add|edit|delete|move), `ruleNo`, `before`, `after`, `by`

## 2. 구조 (모듈 분리)
확정 스택: 브라우저 단독 앱. 서버·빌드 도구·외부 라이브러리 없이 `index.html` 을 더블클릭(file://)해서 실행한다. 순수 HTML + CSS + JavaScript.
- `file://` 에서는 브라우저가 ES 모듈(`type="module"`) 로딩을 막는다. 그래서 일반 `<script src>` 를 순서대로 불러오고, 각 파일은 전역 `PW` 이름공간에 등록한다. Node 에서도 쓸 수 있게 파일 끝에서 `module.exports` 를 조건부로 내보낸다.
- 테스트는 자체 소형 도구(`test/harness.js`)로 작성한다. 기본 실행은 브라우저에서 `test/index.html` 을 여는 것이고, Node 가 있으면 `node test/run-node.js` 로도 돈다. (개발 PC 에 Node 가 없어서 `node:test` 대신 이 방식으로 바꿨다.) 새 모듈을 만들면 `test/index.html` 에 script 를 추가한다. UI 는 수동 확인.
- 정책표·이력은 `localStorage` 에 저장한다(서버 없음).

| 모듈 | 책임 | SPEC |
|---|---|---|
| `topology.js` | 구역·호스트·그룹 데이터, IP→구역, 주소 해석 | 1-4-4, 2 서두 |
| `address.js` | 주소 표현식 → 해석된 집합, `covers`, `matches` | 2-3, 2-7 |
| `service.js` | 서비스 문자열 파싱·범위 포함·일치 | 2-3, 2-7 |
| `engine.js` | first-match 판정, trace 생성 | 2-1 |
| `analyzer.js` | 기본 거부 검사, 섀도잉, 중복, syslog 검사 | 2-2~2-4, 2-6 |
| `validator.js` | 입력 검증(알 수 없는 주소, 서비스 형식 오류) | 2-7 |
| `history.js` | 변경 이력 기록 | 2-5 |
| `policy.js` | 정책표 편집(추가·수정·삭제·이동)과 이력 연동 | 2-5 |
| `ui/` | 토폴로지 그림, 정책표, 패킷 입력, 결과, 이력 화면 | 3 |

규칙: `engine`·`analyzer`·`history` 는 화면(DOM)을 모르는 순수 함수. UI 는 이들을 호출만 한다.

## 3. 판정 엔진 (first-match) [SPEC 2-1]
1. 패킷의 송신·수신 IP 를 구역·그룹과 대조해 해석한다.
2. 규칙을 번호 오름차순으로 순회하며 출발지·목적지·프로토콜·포트가 모두 일치하는지 본다.
3. **처음 일치한 규칙 하나**의 동작을 결과로 하고 **즉시 중단**한다. 아래 규칙은 보지 않는다.
4. 일치 규칙이 없으면 `matched=null, action=deny` 와 경고 "일치 규칙 없음 — 기본 거부 규칙 필요".
5. 순회 중 건너뛴 규칙과 불일치 사유(출발지/목적지/서비스)를 `trace` 에 담아, 화면에서 "패킷이 어느 규칙에서 멈췄는지"를 길로 보여준다.
- 허용 규칙 아래에 같은 범위의 차단 규칙이 있어도 결과는 허용(순서가 결과를 바꾼다)임을 테스트로 고정한다.

## 4. 정책 점검 (분석기) [SPEC 2-2~2-4, 2-6]
정책표 전체를 입력받아 경고 목록을 돌려준다. 문구는 SPEC 과 글자 그대로 일치시킨다.

### 4-1. covers 계산
- 주소: 규칙의 출발지/목적지를 (구역 집합, IP 집합)으로 풀어 A 가 B 를 포함하는지 판정. Any 처리는 SPEC 2-3 의 covers 정의를 그대로 따른다.
- 서비스: 프로토콜별 포트 범위 병합 후, B 의 모든 범위가 A 의 같은 프로토콜 범위 안에 있는지 확인. A 가 Any 면 참.

### 4-2. 검사 순서
| 검사 | 조건 | 경고 |
|---|---|---|
| 기본 거부 | 마지막 규칙이 Any-Any-Any 차단이 아님 | 마지막 Any-Any 차단(기본 거부) 규칙이 없습니다 |
| 섀도잉 | 위 규칙 i 가 j 의 출발지·목적지·서비스를 모두 덮고 동작이 **다름** | 규칙 j 는 규칙 i 에 가려져 절대 적용되지 않습니다(섀도잉) |
| 중복 | 위 규칙 i 가 j 를 모두 덮고 동작이 **같음** | 규칙 j 는 규칙 i 와 중복입니다(같은 트래픽·같은 동작) |
| syslog | 로그 수집 규칙의 UDP 포트에 514 없음 | 규칙 n: syslog 표준 포트가 아님 (UDP 513 → 표준 포트는 UDP 514) |

- 섀도잉과 중복은 동작이 다른지 같은지만 갈린다. 한 쌍(i, j)은 둘 중 하나로만 보고한다.
- 로그 수집 규칙 판별: 목적지가 '보안관제(SIEM)' 그룹 또는 SIEM IP, 또는 목적에 'syslog'/'로그' 포함 [SPEC 2-6].
- 화면에서 정책 점검 버튼 하나가 위 4개를 모두 실행하고, 규칙 행에 경고 배지를 단다 [SPEC 1-5-2].

## 5. 변경 이력 [SPEC 2-5]
- 정책 편집은 모두 `policy.js` 를 거치고, 거기서 `history.js` 로 한 건씩 기록한다. 이력 없이 규칙을 바꾸는 경로를 두지 않는다.
- 이벤트별 기록 내용:
  | 종류 | before | after |
  |---|---|---|
  | add | null | 새 규칙 전체 |
  | edit | 변경 전 규칙 전체 | 변경 후 규칙 전체 |
  | delete | 삭제된 규칙 전체 | null |
  | move | 이동 전 번호의 규칙 | 이동 후 번호의 규칙 |
- 항목: `time`(ISO8601), `type`, `ruleNo`, `before`, `after`, `by`.
- 삭제·이동 후 규칙 번호는 1부터 연속으로 다시 매긴다. 이력의 `ruleNo` 는 변경 시점의 번호.
- 이력은 추가만 가능(수정·삭제 없음). 화면에 시간 역순 표로 보여 준다.
- `by` 는 화면의 '변경자' 입력값. 비어 있으면 저장하지 않고 입력을 요구한다(이력 항목 1-3-4 충족).
- 저장: 우선 메모리 + `localStorage`(정책표와 이력). 서버 없음.

## 6. 입력 검증 [SPEC 2-7]
- 출발지/목적지가 Any·구역 이름·주소 그룹 이름·올바른 IPv4(옥텟 0~255) 중 하나가 아니면 오류 "알 수 없는 주소".
- 서비스가 `Any` 또는 `TCP|UDP 포트[,포트…]`(포트 1~65535) 형식이 아니면 오류 "서비스 형식 오류".
- 검증 실패 시 정책표와 이력은 변하지 않는다.

## 7. 화면 구성
1. **토폴로지**: 4구역을 방화벽 중심으로 그린 SVG. 패킷 판정 후 출발 구역 → 방화벽 → 목적 구역으로 경로를 색(허용=초록, 차단=빨강)으로 표시.
2. **정책표**: 5행 기본표를 표시·편집. 행 추가·수정·삭제·위/아래 이동. 경고 배지.
3. **패킷 길찾기 패널**: 출발 IP, 목적 IP, 프로토콜, 포트 입력 → 판정 결과, 일치 규칙 번호, trace(규칙별 통과/불일치 사유).
4. **정책 점검** 버튼: 경고 목록.
5. **변경 이력** 표.
- 교육용 앱이므로 화면 문구에 SPEC 번호(예: [1-1-1])를 작게 병기해 근거를 보여 준다.

## 8. 테스트 계획
SPEC 3절의 함정 3개를 가장 먼저 자동 테스트로 만든다.

| # | 테스트 | 기대 결과 | SPEC |
|---|---|---|---|
| T1 | 1번을 Any→Any 허용으로 바꾼 뒤 점검 | 아래 차단 규칙(기본 거부 포함) 전부 섀도잉 경고 | 2-3 |
| T2 | 기본표에서 10.20.1.20 → 203.0.113.10 TCP 443 | 5번 규칙, 차단 | 2-1, 1-2-7 |
| T3 | syslog 규칙 UDP 513 / 514 | 513 은 경고, 514 는 경고 없음 | 2-6 |

추가 테스트:
- first-match: 허용 규칙이 차단 규칙보다 위면 허용, 순서를 바꾸면 차단. 첫 일치 이후 규칙은 평가하지 않음(trace 에 없음).
- 암묵적 차단: 5번을 삭제하고 미허용 패킷 → matched=null, deny, 경고.
- 기본 거부 검사: 마지막 규칙이 Any-Any 차단이 아닐 때 경고, 맞으면 없음.
- 중복: 같은 동작의 포함 관계 규칙 쌍 → 중복 경고, 동작이 다르면 섀도잉.
- covers 경계: Any vs 비-Any, 포트 범위 부분 포함, 구역 vs 단일 IP.
- 이력: add/edit/delete/move 각 1건씩 기록, edit 의 before/after 가 규칙 전체, time 이 ISO8601, 검증 실패 시 이력 없음.
- 입력 검증: 잘못된 IP(`300.1.1.1`), 잘못된 서비스(`TCP`, `TCP 99999`) → SPEC 의 오류 문구.
- 기본 5행 정책표에서 SPEC 1-2 의 구간별 허용 케이스(웹 접속, DB 연동, 관리자 SSH, 로그 수집)가 모두 허용, 역방향은 차단.

## 9. 작업 순서 (마일스톤)
1. 프로젝트 골격(`index.html`, 스크립트 로딩 순서, 테스트 실행 틀)과 `topology.js` 데이터(1절).
2. `address.js`·`service.js`·`validator.js` + 단위 테스트(8절 입력 검증, covers 경계).
3. `engine.js` + T2, first-match 테스트.
4. `analyzer.js` + T1, T3, 기본 거부·중복 테스트.
5. `history.js`·`policy.js` + 이력 테스트.
6. UI: 정책표 → 패킷 패널 → 토폴로지 → 점검·이력 화면.
7. 전체 시나리오 수동 확인, README 에 실행법과 SPEC 번호 대응표 정리.

각 단계는 테스트를 통과한 뒤 커밋한다. SPEC 에 없는 규칙은 구현하지 않는다.
